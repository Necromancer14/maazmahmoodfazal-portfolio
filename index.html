Certificate of insurance agent

Oz, for a US insurance client. 2026.

95%of requests complete through the agent

Servicers handled every certificate of insurance request by hand: read the email, work out what was being asked, build the certificate, send it and file it. I designed an agent that does the routine part and leaves the approval with a person.

How a request moves

  1. An LLM reads the request and classifies its type, holder and requestor.
  2. The agent calls the matching Outmarket.ai workflow through its API to generate the certificate as a PDF.
  3. A servicer opens the portal, checks the PDF and approves, rejects or retries it.
  4. Approved certificates are emailed to the requestor and filed. Every step is written to an audit trail.

Design decisions

  • The LLM decides what is asked, not what the certificate says. The certificate is built by the matching Outmarket.ai workflow, so the model never writes coverage details.
  • A person approves every certificate. A wrong certificate goes to a third party, so the agent prepares the work and a servicer signs it off.
  • Unclear requests go to people instead of a guess. If the agent cannot place a request, it goes to a manual queue.
  • Queued, logged and keyless. Work moves through Service Bus so nothing is lost during spikes or retries, every step is written to Cosmos DB, and services authenticate with managed identities instead of stored secrets.

When it fails

  • Requests the agent cannot place go to the manual queue. That is about 5% today.
  • A servicer can retry a run with changes, which sends it back through orchestration, or reject it to the manual queue.
  • Next, phase 2 is planned to cover the requests that still go to the manual queue.

invoice-desk

Public code and live demo. Python, FastAPI, React. 2026.

0unsafe auto-approvals on 60 test invoices with a known answer key
Try the live demo Read the code

The demo runs on a free server, so the first load can take about a minute. All data in it is made up.

A Saudi e-invoice intake desk. Supplier invoices arrive as text, PDF or phone photo, in English, Arabic or both. A reader pulls out the fields, a rule engine checks them, clean invoices are approved automatically and doubtful ones go to a person. Every decision, human or automatic, is logged.

Design decisions

  • The model proposes, the rules decide. The model only extracts fields. Approval comes from deterministic checks, so a wrong or manipulated extraction is caught by arithmetic and format rules. One test invoice hides an instruction aimed at the model.
  • Rules are data. 14 rule types, including Saudi VAT number format, 15% VAT, line totals and QR code agreement, live in the database. Admins edit them in the portal, a dry run shows how many past decisions would change, and every change is a version that can be restored.
  • Free by default, any model by choice. A built-in reader works with no key. For photos and unusual layouts you can plug in Gemini, Groq, OpenRouter, Ollama, Claude or OpenAI through one interface.
  • Arabic is first class. The whole portal is translated with a right-to-left layout, and CI fails if any screen is missing its Arabic.

Measured results

With an AI model reading the invoices, it made the right decision on all 60 test invoices. The free built-in reader, with no model at all, scores like this:

Synthetic invoicesRight decisionFields correct
All (60)80%81%
Text (40)90%92%
PDF with a text layer (10)100%100%
Photos (10)20%13%

Nothing was wrongly approved or wrongly rejected. What the reader cannot read goes to a person instead of being guessed. Photos are its weak spot, and that is exactly where the AI model closes the gap.

A help-desk agent that answers from a knowledge base, says it does not know when nothing fits, and changes its answers from thumbs up, thumbs down and corrections. Every rating goes into a SQLite log, and the retrieval changes are rebuilt from that log, so any state can be reproduced.
